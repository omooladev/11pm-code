# 🌙 11PM Code

> **Twice a week • 11:00 PM – 12:00 AM**  
> *Consistent practice, problem-solving, experimentation, and learning together.*

---

## 🎯 Core Idea

**11PM Code** is a twice-weekly coding practice session where developers meet at **11:00 PM** and spend one focused hour improving their coding skills.

### The Goal
> **Twice a week, we show up and spend an hour getting better at coding.**

The sessions are not primarily about teaching or producing polished projects. They are about:
- **Consistent habit:** Showing up regularly to write code under a timebox.
- **Problem-solving:** Tackling concrete challenges without relying on tutorial hand-holding.
- **Experimentation:** Trying new approaches, architectures, and libraries.
- **Peer learning:** Seeing how different developers think and solve the same problem.

---

## ⏱️ How a Session Works

### 1. Choose the Challenge (6 Hours Before)
At least **6 hours before** the session, the challenge is decided and shared with everyone participating.

- The challenge is intentionally scoped to be workable within a **30–40 minute** window.
- The challenge document outlines:
  - **Objective:** What we are trying to achieve.
  - **Requirements & Constraints:** Expected inputs, outputs, and behaviors.
  - **Pre-session Context:** Anything participants need to know beforehand.

> **Why the 6-hour head start?**  
> The purpose of preparation is not to copy a solution beforehand—it is to think through the problem, research unfamiliar concepts, and make the live session deeply productive.

#### Challenge Examples
- 🛠️ Build a REST API endpoint
- 🗄️ Write an optimized PostgreSQL query
- ⚛️ Build a reusable React component / modal
- 🐛 Debug and fix a broken feature
- 🔐 Implement token-based authentication
- 🧩 Solve a DSA / algorithmic problem
- 📦 Learn a new library by building something with it
- 🎨 Build a small UI feature or microsite

## 👥 Session Formats

### Format A: Same Problem, Different Solutions *(Default)*
*Two or more developers • One challenge • Independent implementations*

- Everyone works independently on the exact same challenge.
- **Example:** Build a URL shortener API.
  - *Developer 1:* Node.js + PostgreSQL
  - *Developer 2:* Go + SQLite
  - *Or:* Same stack, but completely different architectural & design decisions.
- **Why this works:** Encourages independent critical thinking and creates rich, insightful debriefs (*"Let's see how you solved it"*).

---

### Format B: Build Together *(Collaborative)*
*Two or more developers • One project • One shared codebase*

- Used when the challenge benefits from pair programming or shared architectural work.
- **Example:** Build a live authentication system or complex state machine together using collaborative tooling.

---

## 💬 Review & Discussion Prompts

At **11:40 PM**, coding stops and the debrief begins. We explore:

1. **Approach & Architecture:** What did you build, and why did you choose that approach?
2. **Trade-offs:** Why did you make those specific technical decisions?
3. **Struggles & Debugging:** What broke? What bugs did you encounter, and how did you resolve them?
4. **Refactoring:** What would you change if you had another 30 minutes?
5. **Key Learnings:** What was surprising, difficult, or newly learned?
6. **Future Improvements:** What could we do better in the next session?

## 📈 Evolution & Growth

### Phase 1: 1-on-1 Practice
- Start with one other developer.
- Focus strictly on coding quality, smooth session flow, and productive discussions.

### Phase 2: Series Identity
- Structure each session as an identifiable edition:
  - **11PM Code #01:** Accessible Popup Dialog & Modal System
  - **11PM Code #02:** Same Backend Problem, Different Solutions
  - **11PM Code #03:** Debugging a Broken Auth Flow

### Phase 3: Streaming & Community (Optional Expansion)
- **Initial Setup:** Google Meet / Discord (Voice, screen sharing, and recording via platform tools or OBS).
- **Future:** Stream publicly via OBS to YouTube Live once the format is battle-tested.

## ⚡ Practical Reality & Resilience

The sessions are built to succeed under real-world constraints:

- 💡 **Full Power & Internet:** Code normally.
- 🔋 **Power Outage (Laptop Charged):** Continue coding offline.
- 📶 **Weak Connection:** Use mobile hotspot or switch to local offline builds.
- 🛠️ **Severe Technical Friction:** Pivot session to code review, architecture planning, or debugging past code.
- 🔁 **Total Failure:** No problem. Regroup and return for the next scheduled session.

> **Objective: Consistency over perfection.**
